# Подготовка выпуска 1.0.0

Исходники подготовлены к версии `1.0.0`. Это инструкция проверки и публикации: наличие файла не означает, что тег, GitHub Release или боевое развёртывание уже созданы. Список возможностей находится в [CHANGELOG.md](CHANGELOG.md).

## Состав выпуска

- Приложение Django 5.2 / Python 3.13 с учётом запчастей, ролями, проверкой заявок, инвентаризацией, отчётами и XLSX.
- Контейнерный образ `warehouse-django:1.0.0`; версия в `warehouse/__init__.py` и OCI-метаданных образа.
- PostgreSQL 17 с постоянным томом, проверками готовности и отдельным сервисом инициализации; SQLite остаётся совместимым локальным вариантом.
- Конфигурации `compose.yaml`, `compose.dev.yaml`, `compose.production.yaml`, примеры `.env` и инструкция работы за Nginx/HTTPS.
- Автоматические проверки CI и инструкции проверяемого резервного копирования/восстановления.

## Проверка перед публикацией

Проверки выполняйте на отдельном стенде с новой БД, тестовыми секретами и свободным портом. Рабочую базу и её том для этого не используйте. Все команды приведены из корня репозитория; после подготовки `.env` по [README](README.md) поднимите стандартный стенд:

```sh
docker compose config --quiet
docker compose up -d --build --wait
docker compose exec web python -m pip check
docker compose exec web python manage.py check
docker compose exec web python manage.py makemigrations --check --dry-run
docker compose exec web python manage.py test
docker compose exec -T web python deploy/smoke.py
docker compose exec web python -c "from warehouse import __version__; print(__version__)"
docker compose ps -a
```

Тесты создают отдельную тестовую БД; пользователь стандартного контейнера имеет необходимые права. Для внешней PostgreSQL используйте отдельного тестового пользователя с правом создания БД. Проверка возвращаемой версии должна показать `1.0.0`. У `init` ожидается код завершения 0, у `db` и `web` — состояние healthy. Если перед этим работал другой Compose-стенд, сохраните его данные и используйте согласованные имя проекта и порт; не удаляйте томы ради повторной проверки.

До публикации должны быть проверены:

- Сборка образа, совместимость зависимостей, системные проверки Django, отсутствие незаписанных миграций и тесты на PostgreSQL.
- Повторный запуск Compose с сохранением записей в БД; корректный отказ запуска при отсутствующих секретах и ошибочной production-конфигурации.
- Dev-конфигурация: загрузка приложения, перезагрузка кода и доступ к БД на loopback из IDE.
- Production-конфигурация: `check --deploy --fail-level ERROR`, готовность через HTTPS-прокси и загрузка статических файлов.
- Создание администратора, вход, назначение ролей и основные операции склада: приход, расход, заявка, перемещение, инвентаризация, отмена и отчёт XLSX.
- Создание `pg_dump` и восстановление в новую БД отдельного проекта с проверкой пользователей, документов, остатков и готовности приложения.
- Локальная совместимость с SQLite, включая её миграции и тесты.

Успех отдельных автоматических тестов не заменяет проверку HTTPS/DNS, рабочего резервного хранилища и целевой конфигурации на сервере. Результат фактического прогона сохраняется с выпуском; проверки, которые ещё не выполнены в целевой среде, отмечаются отдельно.

## Данные и ограничения

Прежний том SQLite `warehouse-data` и файл `db.sqlite3` не используются новым Compose и не переносятся автоматически. Не удаляйте их. Если существующая установка содержит данные, переход на PostgreSQL выполняется отдельно с резервной копией и сверкой документов, остатков, учётных записей и прав.

PostgreSQL хранит данные в томе `warehouse-postgres-data` внутри выбранного Compose-проекта. Команда `down -v` удаляет эти данные. Обновление пароля в `.env` не меняет пароль в уже созданной PostgreSQL — изменение нужно выполнить согласованно в базе и конфигурации.

Складские записывающие транзакции PostgreSQL используют общую блокировку до завершения транзакции: одновременно выполняется одна такая операция, а чтения могут выполняться параллельно. Это сохраняет последовательную обработку складских изменений при нескольких процессах Gunicorn. Обновления напрямую через SQL или `bulk_create` обходят модельные проверки и блокировку; такие импорты требуют отдельной остановки записей и сверки данных. Пропускная способность записи ограничена последовательным выполнением этих транзакций.

Миграции могут менять схему данных. Для отката нужны сохранённый прежний образ и проверенная копия БД; переключение тега образа само по себе не откатывает схему. Порядок сохранения образа и контрольного восстановления приведён в [deploy/README.md](deploy/README.md).

Файл лицензии для собственного кода проекта пока не выбран. Это открытое решение владельца; в подготовку версии новая лицензия не добавлялась. Лицензии включённых сторонних библиотек сохраняются в `static/libs/`.

## Коммит, тег и GitHub Release

Следующие действия выполняются владельцем после проверки изменений и одобрения публикации. Команды ниже выполняются в одной сессии Bash (в Windows — Git Bash). Сами инструкции ничего не публикуют.

1. Просмотрите `git status --short`, `git diff` и результаты проверок. Убедитесь, что `.env`, приватные ключи, дампы и реальные данные не попали в индекс. Добавьте в индекс только проверенные файлы, перечислив их явно: `git add -- ПУТЬ_К_ФАЙЛУ ...`.
2. Создайте релизный коммит и проверьте, что рабочее дерево чистое:

   ```sh
   git commit -m "Release v1.0.0"
   git status --short
   release_commit="$(git rev-parse HEAD)"
   printf 'Release commit: %s\n' "$release_commit"
   ```

3. После согласования отправьте коммит в выбранную релизную ветку и дождитесь успешного CI именно для SHA, записанного в `release_commit`. Для текущей релизной ветки:

   ```sh
   release_branch="$(git branch --show-current)"
   test -n "$release_branch"
   git push --set-upstream origin "$release_branch"
   ```

4. После успешных проверок создайте аннотированный тег на проверенном коммите и отправьте его в репозиторий:

   ```sh
   git tag -a v1.0.0 "$release_commit" -m "Склад запчастей 1.0.0"
   git push origin v1.0.0
   ```

5. На GitHub откройте Releases → Draft a new release, выберите существующий `v1.0.0`, задайте заголовок «Склад запчастей 1.0.0» и скопируйте описание из `CHANGELOG.md`. Укажите фактические результаты проверок и ограничения перехода с SQLite, затем опубликуйте выпуск. Если используется GitHub CLI, черновик можно подготовить так (параметры описаны в [справочнике GitHub CLI](https://cli.github.com/manual/gh_release_create)):

   ```sh
   gh release create v1.0.0 --repo Chvanigus/warehouse-django --verify-tag --draft --title "Склад запчастей 1.0.0" --notes-file CHANGELOG.md
   ```

Публикация исходников/тега и загрузка образа в реестр — отдельные действия. Compose собирает образ локально; адрес реестра и автоматическая публикация контейнера этой инструкцией не задаются. Боевой сервер разворачивается отдельно по [deploy/README.md](deploy/README.md).
