# Развёртывание склада

Конфигурация рассчитана на один Linux-сервер с Docker Compose и обратным прокси Nginx на хосте. Gunicorn использует один процесс и четыре потока. Для SQLite выделен именованный том на локальном диске. Запускайте один экземпляр приложения на том и сохраняйте резервные копии отдельно от сервера.

## Первый запуск

1. Скопируйте `.env.example` в `.env`. Установите доступ к файлу только для владельца (`chmod 600 .env`), заполните `WAREHOUSE_PUBLIC_HOST` вашим доменом и задайте случайный `SECRET_KEY`, например через `python3 -c 'import secrets; print(secrets.token_urlsafe(64))'`. Если порт 8000 занят, смените `WAREHOUSE_PORT` и порт upstream в Nginx.
2. Настройте DNS и действующий TLS-сертификат. Подключите [пример Nginx](nginx.conf.example) в блок `http`, подставьте домен и пути к сертификату. Выполните `nginx -t` перед перезагрузкой конфигурации. Прокси заменяет `X-Forwarded-Proto`, ограничивает размер запроса и частоту попыток входа. Compose публикует Gunicorn на `127.0.0.1` хоста.
3. Выполните команды из корня проекта в одной сессии Bash. Пароль первого администратора задаётся в интерактивном приглашении.

```bash
dc() { docker compose -p warehouse -f compose.yaml -f compose.production.yaml "$@"; }
dc build --pull
dc run --rm web python manage.py check --deploy --fail-level ERROR
dc run --rm web python manage.py migrate --noinput
dc run --rm web python manage.py configure_warehouse_roles
dc run --rm web python manage.py createsuperuser
dc up -d --wait
```

`check --deploy` может показать рекомендации о распространении HSTS на поддомены и включении preload. Эти параметры задаются отдельно для доменной зоны. При запуске контейнер проверяет миграции, а `up --wait` ждёт успешного ответа `/healthz/`. Проверьте этот адрес через публичный HTTPS и войдите в приложение. Создайте обычного администратора склада через «Управление» и проверьте вход под каждой ролью.

## Резервная копия и обновление

Для плановой копии можно оставить сервис запущенным. Команда использует SQLite Online Backup API и проверяет целостность снимка до его публикации. Для обновления зафиксируйте прежний коммит и тег образа, соберите целевую версию командой `dc build --pull` и остановите старый контейнер перед созданием снимка. Используйте постоянное имя проекта Compose.

```bash
dc stop web
snapshot="warehouse-$(date -u +%Y%m%dT%H%M%SZ).sqlite3"
dc run --rm web python manage.py warehouse_database backup "/data/$snapshot"
dc cp "web:/data/$snapshot" "./$snapshot"
chmod 600 "$snapshot"
```

Сохраните снимок в закрытом хранилище. После проверки внешней копии удалите промежуточный файл из тома командой `dc run --rm web rm -- "/data/$snapshot"`. Сначала проверьте миграции на восстановленной копии и затем примените к рабочему тому команды `check --deploy`, `migrate`, `configure_warehouse_roles` и `up --wait` из раздела первого запуска. При ошибке миграции держите сервис остановленным до исправления или восстановления в новый том с прежним образом.

## Контрольное восстановление

Разверните копию под отдельным именем проекта и портом. Команда `restore` проверяет снимок и создаёт файл базы в пустом томе. Восстановление с прежним образом проверяет возможность отката, с новым — применимость миграций.

```bash
restore() { WAREHOUSE_PORT=18084 docker compose -p warehouse-restore -f compose.yaml -f compose.production.yaml "$@"; }
restore run --rm -T web python manage.py warehouse_database restore - < "$snapshot"
restore run --rm web python manage.py migrate --check
restore up -d --wait
```

Для репетиции обновления выполните `migrate --noinput` и `configure_warehouse_roles` вместо проверки применённых миграций. Сравните остатки, документы и заявки на восстановленном экземпляре перед переключением прокси. При откате сохраните рабочий том для расследования и подключите прокси к проверенному экземпляру со старой версией.

При переходе с ранних версий `python manage.py reconcile_stock` показывает возможные дубли остатков. После сверки с фактическими данными можно явно объединить одну группу командой `python manage.py reconcile_stock --merge ID_СОХРАНЯЕМОЙ_СТРОКИ ID_ДУБЛЯ …`. Документы с будущей датой, проведённые до появления проверки даты, сохраняются с отметкой в журнале.
